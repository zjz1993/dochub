# DocHub 需求说明

## 项目目标

**产品目标**：做一个企业级产品文档管理与发布平台。软件公司用它管理多条产品线、多个产品版本、多种语言的文档，并把已上线版本的已发布内容展示给读者。

**个人目标**：通过真实业务补齐后端工程能力。重点项目结束后你能独立解释并维护：表设计、事务、权限、状态流转、并发控制、测试和部署。

## 核心用户角色

| 角色 | 在哪里 | 能做什么 |
|---|---|---|
| 系统管理员 | 管理端 | 管理产品线、产品版本和用户；可以操作所有内容 |
| 编辑 | 管理端 | 只在自己被分配的产品线里维护分类、文档、语言版本，并发布和下线 |
| 读者 | 展示端 | 不用登录，只看已上线版本的已发布内容 |

## 核心业务流程

**流程 A：一个产品第一次发布文档**

1. 系统管理员建产品线（配置默认语言），给编辑分配该产品线。
2. 系统管理员在产品线下建版本，此时版本未上线。
3. 编辑建分类（可嵌套）和文档；新建文档时自动带上默认语言版本。
4. 编辑写草稿，发布；按需新建其他语言版本并发布。
5. 系统管理员把版本切到上线，读者才能看到。

**流程 B：发布一个新产品版本**

1. 系统管理员从已有版本“复制为新版本”，草稿和已发布内容原样带过来，新版本未上线。
2. 编辑只改有变化的语言版本并重新发布；没改的不用动。
3. 系统管理员把新版本切到上线。

**流程 C：多语言**

- 每个语言版本独立发布、独立下线、独立记修订。
- 读者要的语言没有已发布内容时，展示默认语言的内容并给出提示。
- 原文重新发布后，译文被标记为“原文已更新”。

**流程 D：读者浏览**

- 选产品线 → 切版本 → 切语言 → 在目录树里选文档阅读。目录树里只出现有已发布内容的文档。

## MVP 范围

**第一档：MVP 必做（100 小时）**

| 模块 | 内容 |
|---|---|
| 登录与权限 | JWT 登录；系统管理员和编辑两种固定角色；产品线级的数据鉴权；最小的用户与成员管理 |
| 产品线与版本 | 产品线增改、排序、启停；版本增改、上线、下线、复制 |
| 分类与文档 | 分类树的增删改、移动、排序；分类名按语言存；文档的增删、移动、排序 |
| 编辑 | 语言版本；保存草稿并净化 HTML；图片上传；编辑锁（Redis） |
| 发布与修订 | 发布、下线、修订历史、回滚、译文过期标记 |
| 展示端 | 产品线、版本、语言切换；目录树；正文渲染与默认语言回退 |
| 工程 | 测试；镜像与编排；部署到你的服务器；备份与项目说明 |

**第二档：有时间再做**（用第 11、12 周的缓冲）

全文搜索（标题）、刷新令牌、端到端冒烟测试、修订对比、登录限流、批量发布、强制接管编辑锁、附件上传、由 OpenAPI 生成前端类型、持续集成、迁移到 Spring Boot 4.1、审核流程。

**第三档：后续迭代**

展示端登录与按产品线授权、MinIO、Elasticsearch、多产品线共享文档、跨版本对比、定时发布、可配置的角色权限、服务端渲染以外的性能优化。

**明确不做，以及原因**

| 不做 | 原因 |
|---|---|
| 文档类型字段 | 靠分类区分用户手册和 API 文档 |
| 多产品线共享文档 | 需要时到另一个产品线手动新建 |
| `role`、`permission` 表 | 角色是代码里的固定值，改成可配置是加表而不是改模型 |
| `publish_log` 表 | 修订本身就记录了发布人和时间 |
| 微服务、消息队列 | MVP 不需要 |
| 删除产品线 | 用停用代替，避免误删整条产品线的内容 |

**进度落后时按这个顺序放弃**：译文过期标记 → 回滚 → 用户管理界面（改用脚本建用户）。

## 规模与预算

- 每周 10 小时（工作日每天 2 小时）。任务共 100 小时；第 10 周因春节只有 4 个工作日，最后 2 小时的任务挪到第 11 周。
- 第 11、12 周共 20 小时，扣除挪来的 2 小时，缓冲是 18 小时。
