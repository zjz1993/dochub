# 开发指南

本文件说明这个项目怎么开发：工作流程、分工、环境、命令、测试、提交、进度和风险。做什么见 [overview](./overview.md)，每一块怎么实现见对应变更的 `design.md`。

## 工作流程（OpenSpec）

所有开发工作都通过 `openspec/changes/` 下的变更进行，不直接写代码。每个变更包含四样东西：`proposal.md`（为什么改、改什么）、`specs/`（做完之后系统应该有的行为）、`design.md`（怎么做）、`tasks.md`（任务清单）。

| 步骤 | 做什么 | 产出 |
|---|---|---|
| 1. 开始一周 | 读 `docs/learning/week-NN.md` 和对应变更的四个文件；核对 proposal、specs、design 现在是否仍然成立，不成立先改它们 | 更新后的变更 |
| 2. 实现 | 按任务清单从上往下，一次只做一个；每完成一个就把 `- [ ]` 改成 `- [x]`，Agent 随即输出一份简短的任务复盘 | 代码、测试和任务复盘 |
| 3. 验收 | 对照本周验收标准，跑全量测试 | 通过的验收 |
| 4. 复盘 | 一起过一遍代码质量和架构，连同各任务复盘里“后续改进”的条目，结论写进周文档的复盘记录 | 复盘记录 |
| 5. 归档 | 把变更的规格增量同步到 `openspec/specs/`，变更目录移入 `openspec/changes/archive/` | 更新后的规格 |

规则：

- 同一时间只有一个进行中的变更，按第 1 周到第 10 周的顺序做。路线图里十个变更已经预建好。
- `openspec/specs/` 记录“已经实现”的事实，只能通过归档或同步写入，不要手写需求进去。
- 需要偏离设计时（多一张表、多一个中间件、改接口形状），先改变更的 proposal 或 design。难以逆转的决定在 `docs/decisions/` 记一条 ADR。
- 一个任务一次提交，提交前 `./mvnw test` 必须通过。

### 任务复盘

每完成一个任务，Agent 会输出一份简短的复盘，固定六段：本次任务、涉及知识点、代码审查、开发者需要掌握、学习检查、后续改进。模板和填写约定在 `AGENTS.md` 的「任务复盘」一节。

- **代码审查**分四类：正确性、设计、安全、可维护性。
- **开发者需要掌握**是留给你的自测问题，不给答案。
- **学习检查**四项由你自己勾选。
- **后续改进**里值得留住的条目，周末复盘时带进本周文档的复盘记录。

### OpenSpec 技能与命令行

项目里装了 OpenSpec 的六个技能（`.agents/skills/openspec-*`，`.zcode/skills/` 里是链接）。对 Agent 直接说要做的事即可：

| 时机 | 说法 |
|---|---|
| 开始或继续实现一个变更 | “应用 add-engineering-foundation 变更” |
| 修改变更的计划 | “更新这个变更的设计” |
| 全部任务完成后归档 | “归档这个变更” |
| 为新功能建一个变更 | “提议一个变更：……” |
| 动手之前先把想法想清楚 | “先探索一下……” |

技能的步骤和下面的“分工”冲突时，以分工为准：标注“你写”的任务由你实现，Agent 负责讲解和审查，验证通过之后才勾选。

OpenSpec CLI 已全局安装（2.1.1），需要 Node 22.20 以上。全局安装绑定在 nvm 的 Node 24 上，而终端默认是 20，所以仓库根目录有 `.nvmrc`，进入项目先 `nvm use`：

```bash
nvm use                                          # 切到 .nvmrc 指定的 Node 24
openspec status --change <变更名>                  # 四个产出的完成情况
openspec instructions <产出> --change <变更名>      # 内置的写法说明：proposal / specs / design / tasks / apply / archive
openspec validate --all --strict                  # 校验全部变更和规格
openspec list --changes                           # 进行中的变更
openspec archive <变更名>                         # 归档：同步规格并移入 archive/
```

项目配置在 `openspec/config.yaml`，技能和命令行都会读到它：`context` 会注入到每次生成或应用变更的指令里；`rules` 是针对单个产物的附加规则；`operations` 是应用和归档时的提示。

## 分工

| 标注 | 含义 | 每个任务的流程 |
|---|---|---|
| 你写 | 业务逻辑，由你亲手写 | AI 讲目标和知识点 → 你设计或实现 → AI 审查 → 你修改 → 提交 |
| 你设计 | 先在纸上设计，经审查再写代码 | 你写设计说明 → AI 审查 → 你实现 |
| AI 写 | 前端和样板代码 | AI 写 → 你跑通并对照验证方式 → 提修改意见 → 提交 |
| 你操作 | 在你的服务器上执行 | AI 给出命令和清单 → 你确认 → 你执行 → 一起验证 |

AI 写的范围：全部前端；构建与配置文件、Dockerfile、通用返回与异常处理、测试脚手架、实体和 DTO、薄 Controller。
你写的范围：表设计、SQL、Service 逻辑、权限校验、事务，以及它们的测试。任务行里都有标注，以标注为准。

## 常用命令

项目脚手架搭好之后以实际为准。

```bash
nvm use                                              # 仓库的 .nvmrc 指定 Node 24
docker compose --env-file .env -f deploy/compose.dev.yml up -d   # 本地基础设施：MySQL（127.0.0.1:3306）、Redis（127.0.0.1:6380）
cd backend && ./mvnw spring-boot:run                # 启动后端（dev）
cd backend && ./mvnw test                           # 全量测试
cd frontend && pnpm install && pnpm dev             # 启动前端
```

## 测试策略

- **单元测试**（不起 Spring，速度快）：只测纯逻辑，例如译文是否过期的判断、目录树的组装和标题回退、环检测、HTML 净化的结果。
- **集成测试**（用 Testcontainers 起真实的 MySQL 和 Redis）：权限隔离、发布与下线、回滚、默认语言回退、复制版本、编辑锁的争抢和过期、唯一约束冲突。
- 测试和文档跟随所属的任务组，不堆到最后。每个内容接口至少有一条“外产品线编辑 403”的测试。
- 前端测试：MVP 不写前端单测；端到端冒烟测试放在第二档。

## 提交约定

- 一个任务一次提交，提交信息写明变更名和任务，例如 `feat(access-control): 2.1 密码加密与登录接口`。
- MVP 期间直接在 `main` 上提交。开始做第二档的功能时再为每个变更开分支。
- 不提交密钥、服务器登录信息和 `.idea/`。

## 风险和难点

| 风险 | 会怎么出错 | 预防方法 |
|---|---|---|
| 产品版本与文档修订混淆 | 把“发布”“上线”“回滚”混着用，表里多出版本字段 | 严格用 `docs/domain-model.md` 的词：发布针对语言版本，上线针对产品版本，修订是发布的快照 |
| 多语言数据关系设计不合理 | 标题和分类名没有按语言存，英文站显示中文目录 | 语言版本用 `(document_id, locale)` 唯一；分类名单独一张表；第 9 周的回退测试覆盖“语言缺失” |
| 草稿和发布内容混在一起 | 展示端读到草稿 | 线上内容只存在于修订表，通过指针读取；展示端接口没有任何查草稿的路径 |
| 数据权限校验不完整 | 编辑改一下地址里的 id 就改了别的产品线 | 所有内容接口都走 `AccessChecker`；每个接口都有“外产品线编辑 403”的测试；展示端每个接口先校验“已上线” |
| 事务使用不合理 | 发布只写了一半；同类内部调用导致事务没生效 | `docs/database-conventions.md` 列出的事务场景必须用事务；任务 2.1（`add-document-publishing`）里人为制造失败验证回滚；事务里不调 Redis |
| 接口和数据库过度设计 | 为了灵活做角色表、权限表，拖慢进度 | `docs/overview.md` 列了明确不做的项；需要时再加表 |
| 复制版本的 id 映射出错 | 新版本的数据指回旧版本 | 先做任务 1.1（`add-version-clone-and-tree-ui`）的纸上设计并经审查；任务 1.2（`add-version-clone-and-tree-ui`）的测试断言结构和内容一致、指针指向新版本 |
| 编辑锁的竞态 | 过期的持有者续上或删掉别人的锁 | 续期和释放都用 Lua 比较令牌；每次写草稿和发布都在后端校验持锁；查锁与写库之间的空档已知并接受，见 ADR-004 |
| 富文本 XSS | 编辑者粘贴的内容里带脚本，发布后读者执行 | 保存时白名单净化，并有样本测试；展示端渲染时再净化一次 |
| 令牌被窃取 | JS 读到令牌 | httpOnly Cookie；管理端不渲染未净化的 HTML |
| 登录接口被暴力尝试 | 公网部署后被刷密码 | MVP 没有限流。管理口令用长随机串；限流放进第二档 |
| Spring Boot 3.5 没有安全补丁 | 漏洞无人修 | 见 ADR-005：不放敏感数据，生产环境关闭接口文档，只公开展示端；第 11、12 周可以升级到 4.1 |
| 时间超支 | 某个任务卡住一周 | 每周对照验收标准；按 `docs/overview.md` 的放弃顺序缩减；20 小时缓冲 |
| 服务器资源不够 | 新服务把原有服务挤崩 | 任务 2.1（`add-deployment`）的预检门槛不达标就不部署；镜像在 Mac 上构建；每个容器设内存上限 |
| Textory 集成问题 | React 19 或 Next.js 16 下编辑器异常 | 任务 3.1（`add-product-management`）里提前验证；编辑器只以客户端组件渲染；有问题回 Textory 仓库修、发版、再升级 |
