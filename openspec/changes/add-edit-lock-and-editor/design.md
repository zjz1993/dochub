# Design

## Context

动机，以及“为什么是编辑锁、为什么是 Redis”，见 `docs/decisions/ADR-004-edit-lock-stored-in-redis.md`。接口见 `docs/api-conventions.md`。

## Goals / Non-Goals

**Goals:**
- 任何时刻最多一个人持有某个语言版本的锁。
- 编辑器关闭或崩溃后，锁在几分钟内自动释放。
- 不在编辑的人不会长期占着锁。

**Non-Goals:**
- 强制接管、多人协同编辑、锁的排队等待。

## Decisions

1. **锁是一个带过期时间的租约：获取用 `SET key token NX EX 300`。** 续期和释放各是一段 Lua，值等于自己的令牌才操作。令牌由用户 id 加一个随机串组成，用来防止已经过期的持有者续上或删掉别人的锁。这是 ADR-004 指出的两个坑之一。
2. **只有最近 5 分钟内有操作时才续期，心跳每 60 秒一次。** “开着编辑器”不等于“在写”：去开会、下班忘了关，都会把同事挡在外面。空闲超过阈值后，前端转为只读并停止心跳；点“继续编辑”时重新获取。
3. **获取失败返回 409 和持有者信息。** 另外保存一个带同样过期时间的持有者信息键，用来显示谁从几点开始编辑。
4. **每次写草稿和发布都在后端校验持锁，请求头 `X-Lock-Token` 带令牌。** 只在打开编辑器时检查不够：请求可以不经过页面直接发出。
5. **查锁放在数据库事务之外。** 先查锁再写库是两步，中间有毫秒级的空档：锁刚好过期、被他人取走，原持有者的写入仍然落库。后果只是一次草稿被覆盖，已知并接受。把 Redis 调用放进事务只会放大问题。
6. **锁的粒度是语言版本。** 中文版被锁，不影响别人编辑英文版。
7. **离开页面时尽力释放，失败也没关系，过期兜底。**
8. **测试用 Redis 容器**，覆盖：并发获取只有一个成功、非持有者续期与释放无效、过期后可被他人获取、未持锁保存被拒。

## Risks / Trade-offs

- [浏览器节流后台标签页的定时器，心跳变慢导致锁意外过期] → 过期时间 300 秒、心跳 60 秒，留了四倍余量。被他人取走后，原编辑者的下一次保存会收到 409 并转为只读。
- [Redis 不可用时没人能编辑] → 健康检查暴露 Redis 的状态；锁服务失败时返回 503，而不是放行。
- [跨系统的空档] → 已知并接受，写进了 ADR-004。
- [编辑器在 Next.js 16 下的集成问题] → 已在第 3 周提前验证；编辑器只以客户端组件渲染。
