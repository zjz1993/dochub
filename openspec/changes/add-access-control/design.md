# Design

## Context

动机见 proposal.md。接口见 `docs/api-conventions.md` 的“认证”“用户”两节，表结构见 `docs/database-conventions.md`。

## Goals / Non-Goals

**Goals:**
- 令牌不被页面脚本读到。
- 禁用一个用户后，他的下一次请求就失效。
- 后面所有接口复用同一套“当前用户”和角色判断。

**Non-Goals:**
- 数据范围校验（编辑能访问哪些产品线），留给 `add-product-management`。
- 刷新令牌、登录限流、更多角色，都在第二档或以后。

## Decisions

1. **令牌放 httpOnly Cookie，不放 Authorization 请求头。** 管理端要渲染编辑者写的富文本，脚本读得到的令牌有被窃取的风险；前后端同源部署，Cookie 不需要额外的跨域配置。代价是无状态令牌登出后不能作废，所以有效期定为 8 小时。请求头加本地存储是多数教程的做法，但脚本可读。
2. **`SameSite=Strict`，生产环境加 `Secure`，不开跨域。** 管理接口只接受 JSON 请求体：跨站的表单提交带不上 Cookie，跨源的 JSON 请求会卡在预检上。所以不额外实现 CSRF 令牌。
3. **过滤器每次请求查一次用户。** 多一次主键查询，换来“禁用立即生效”和“角色变更立即生效”。只信令牌里的声明要等到令牌过期才生效。
4. **JWT 用 HS256，密钥来自环境变量，至少 32 字节。** 只有一个后端实例，对称密钥足够。载荷只放用户 id 和角色。
5. **角色是代码里的固定值，不做角色表和权限表。** 接口级用方法级鉴权；数据级在下一个变更里集中到 `AccessChecker`。
6. **登录失败不区分原因。** 用户不存在和密码错误返回同一句话，避免被用来枚举账号。
7. **种子账号只在 dev profile 的初始化器里创建，不写进迁移脚本。** 迁移会在生产环境执行。
8. **`product_line` 表随本变更建立。** 成员表要引用它。它的接口在下一个变更实现，避免为一个外键分两次迁移。

## Risks / Trade-offs

- [无状态令牌无法主动吊销] → 有效期 8 小时；禁用靠每次查库生效；刷新令牌放在第二档。
- [Cookie 依赖同源] → 开发环境由 Next.js 代理 `/api`，生产环境由 nginx 分流，见 `docs/architecture.md`。
- [BCrypt 默认强度拖慢单元测试] → 单元测试用较低的强度因子，集成测试用默认值。
- [Security 配置出错，把所有接口都放开或都拦住] → 每类接口至少一条 401、403、200 的测试，作为回归网。
