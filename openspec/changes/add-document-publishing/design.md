# Design

## Context

动机见 proposal.md。接口见 `docs/api-conventions.md` 的“发布与修订”，表结构和事务场景见 `docs/database-conventions.md`。

## Goals / Non-Goals

**Goals:**
- 读者看到的内容永远是某一条完整的修订，不会是写了一半的状态。
- 每一次上线都有据可查，能回到任意一次。
- 发布和回滚各自是一个事务。

**Non-Goals:**
- 审核流程、定时发布、修订之间的文本对比、草稿的历史。

## Decisions

1. **线上内容只存在于修订表里，语言版本只存一个指针。** 没有第二份可以改动的线上正文，草稿怎么改都影响不到读者。替代方案是在语言版本上存“线上正文”和“草稿正文”两个字段，直观，但两个大字段要反复复制，也多出一条可能被误改的路径。
2. **修订只插入，不更新、不删除。** 删除文档时随语言版本级联删除，是唯一的例外。
3. **只在发布时产生修订，保存草稿不产生。** 草稿的中间状态价值低；以后编辑器做自动保存，每次保存都记会让修订表迅速膨胀。修订有三种来源：发布、回滚、复制版本时带入。
4. **发布在一个事务里完成：插入修订，更新指针、发布时间、发布人。** 测试里人为让第二步失败，验证修订不残留。
5. **回滚是让线上指向一条新的“回滚”修订，内容取自目标修订。** 不删除新修订，也不修改草稿：回滚解决的是线上问题，编辑手里的草稿可能正写着别的东西。
6. **发布必须持有编辑锁；下线和回滚不需要。** 后两者不动草稿。
7. **译文是否过期的判定：译文发布时记下原文当时的线上修订；原文的线上修订变了，译文就是过期。** 只看已发布的内容：原文的草稿改了但没有发布，不算过期。规则写成纯函数。过期的译文重新发布即清除标记。
8. **删除文档的保护在这里补上。** 有任何已发布的语言版本就不能删除，否则返回 409。想删除，先下线。

## Risks / Trade-offs

- [`@Transactional` 失效而不自知：同类内部调用、异常被吞、受检异常不回滚] → 有一条“事务第二步失败”的测试；跨 Service 调用，不在同一个类里自调用。
- [原文回滚后，译文被标记为过期，而内容其实和更早一次相同] → 接受这个误报，译文重新发布即可。
- [修订表随发布次数增长] → 每条是一次完整的正文，量级可控；保留策略放到以后。
- [回滚与发布同时发生] → 两个事务各自完整，后提交的生效；接受。
