# Design

## Context

动机见 proposal.md。接口见 `docs/api-conventions.md` 的“分类与文档”，表结构见 `docs/database-conventions.md`。

## Goals / Non-Goals

**Goals:**
- 树的读写简单可测：一次查询取回，在内存里组装。
- 非法的结构（成环、跨版本挂载）在入口被拒绝。
- 所有内容接口经过同一个数据范围校验。

**Non-Goals:**
- 文档的标题、正文、语言版本（第 5 周）。
- 分类嵌套深度的限制。

## Decisions

1. **分类用自引用外键存树；文档是分类下的叶子，不是树节点。** 分类可以任意嵌套，文档不能再有下级。参考产品（帆软文档）就是这个形态。让文档也能当父节点会更灵活，但两类节点的规则要分别处理，MVP 用不上。
2. **树一次查全、内存组装，不用递归查询。** 一个版本通常只有几十到几百个节点，两条查询加一次内存组装最简单，也避开 N+1。递归 CTE 作为知识点了解即可。树的组装写成纯函数，直接做单元测试。
3. **移动分类时做环检测：目标不能是自己或自己的子孙。** 从目标的父链往上走，碰到自己就拒绝。
4. **文档上冗余 `product_version_id`。** 文档已经通过分类归属于一个版本，再存一份版本 id 是为了按版本查文档时不用联表、快速做归属校验、让 `doc_key` 在版本内唯一。代价是“文档的版本必须等于它所属分类的版本”这条规则只能靠 Service 校验，数据库约束保证不了。这是本变更最需要测试的一条不变量。
5. **`doc_key` 用 UUID，创建后不变，复制版本时原样带走。** 展示端地址用它而不是自增 id：切换版本时，同一个 `doc_key` 能定位到同一篇文档。
6. **移动和重排在一个事务里重排目标同级的全部顺序值。** 同级数量小，整体重排比维护间隔值简单，也不会把间隔用完。
7. **删除分类必须是空的，RESTRICT 外键兜底。** 删除文档此刻直接删，等发布能力上线后再加“已发布不可删”的保护。

## Risks / Trade-offs

- [冗余的版本 id 与分类的版本不一致] → 新建和移动文档时都校验，各有一条集成测试。
- [版本极大时内存组装变慢] → 节点数上千之前不处理；需要时再加缓存或按子树加载。
- [重排整个同级列表写入行数多] → 在一个事务里完成；同级通常不超过几十行。
