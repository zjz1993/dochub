# Design

## Context

动机见 proposal.md 和 `docs/decisions/ADR-002-document-versioning.md`。数据之间的关系见 `docs/database-conventions.md` 的 ER 图。

## Goals / Non-Goals

**Goals:**
- 复制之后，两个版本在结构、内容和发布状态上完全一致，并且互相独立。
- 要么全部复制成功，要么什么都不留。

**Non-Goals:**
- 跨版本的差异对比，以及把修改从旧版本合并到新版本。

## Decisions

1. **整个复制是一个数据库事务。** 步骤的顺序由外键决定：新建版本 → 分类（先父后子）→ 分类名称 → 文档 → 语言版本 → 修订。几百个节点、每种语言一条正文，事务的大小可以接受。
2. **用内存里的映射表换 id：旧分类、旧文档、旧语言版本、旧修订，各自映射到新的 id。** 每个子分类的上级 id、每个文档的分类 id、每个语言版本的文档 id、修订的指针，都要换成新的。漏掉任何一处，数据就会指回旧版本。所以先写出这张映射的设计，经过审查再动手。
3. **只给有线上内容的语言版本生成修订，来源标为“复制”。** 历史修订不复制：新版本的历史从复制那一刻开始。译文的过期指针按规则映射：原文在旧版本里是最新的，就指向新版本里对应的那条复制修订；原文已经更新过，就置空，新版本里同样显示为过期。
4. **`doc_key` 原样带走。** 新版本里 `doc_key` 仍然唯一。展示端切换版本时靠它定位同一篇文档。
5. **复制来的草稿不算“有未发布修改”。** 把草稿的更新时间设成与发布时间相同，否则新版本里的每一篇都会显示成“改了没发”。
6. **编辑锁不复制。** 锁在 Redis 里，以语言版本的 id 作为键。
7. **版本列表的两个统计用两条计数查询实现。** “未发布修改”的判定和目录树上的标记共用同一条规则。
8. **目录树页用 Ant Design 的 Tree，开启拖拽。** 拖拽结束后调用移动接口；非法的移动按接口返回的 400 给出提示。

## Risks / Trade-offs

- [id 映射漏掉一处] → 设计时把所有引用列出来逐一核对；测试断言新版本里每条数据的上级引用都指向新版本。
- [事务中途失败] → 整体回滚，不会留下半个版本。测试覆盖“复制失败后不留下任何数据”。
- [复制期间锁住了源版本的行，影响其他人在源版本上的编辑] → 复制通常在一秒内完成；必要时可以要求复制时源版本没有正在进行的编辑。
