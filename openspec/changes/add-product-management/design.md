# Design

## Context

动机见 proposal.md。接口见 `docs/api-conventions.md` 的“产品线与版本”，表结构见 `docs/database-conventions.md`。

## Goals / Non-Goals

**Goals:**
- 一个集中的入口判断“这个用户能不能访问这条产品线”，后面的内容接口全部复用。
- 版本有一个明确的开关，决定它对读者是否可见。
- 管理端能登录，并完成产品线、版本、用户的日常管理。

**Non-Goals:**
- 复制版本（第 8 周，那时文档和发布都已具备）。
- “产品线管理员”这类更细的角色。

## Decisions

1. **数据范围以产品线为单位。** `AccessChecker` 提供按产品线、版本、分类、文档、语言版本 id 判断的方法，内部都归结到产品线：系统管理员直接通过，编辑查成员表。分类、文档、语言版本都唯一地归属于一条产品线，查一次就够。以文档或分类为单位没有必要，也难维护。
2. **无权访问返回 403，不是 404。** 管理端是内部系统，不隐藏资源是否存在，明确的 403 更容易排查。展示端相反，未上线的内容返回 404。
3. **产品线只停用、不删除。** 删除会带走全部版本和文档，风险远大于收益。
4. **版本的状态只有未上线、已上线两个值，由系统管理员切换。** 版本名形如 `2.0.0`、`2025`、`v3`，不能按字符串排序，顺序由人通过排序值指定。
5. **版本只能在“未上线且没有文档”时删除。** 用来清理建错的空版本；上线过或有内容的版本只能下线。
6. **`code` 创建后不可修改。** 它出现在展示端的地址里。
7. **版本列表的统计字段先占位。** 文档数和未发布修改数依赖后面才建的表，现在返回 0，第 8 周补上计算，避免接口形状中途改变。
8. **管理端在第三周建立，并把编辑器的验证提前。** 编辑器要到第 6 周才正式接入，但它能否在 Next.js 16 和 React 19 下以客户端组件正常工作，是全项目最大的集成不确定点，提前到骨架阶段验证。展示端的只读渲染用哪种方式（发布 `@textory/standalone`，或使用 `editable={false}` 的编辑器）在第 9 周前决定。

## Risks / Trade-offs

- [某个新接口漏掉 `AccessChecker`] → 内容接口的 Controller 只调用经过校验的 Service 方法；每个内容接口都要有一条“外产品线编辑 403”的测试。
- [越权检查要多查一次库] → 都是主键或索引查询，MVP 不做缓存。
- [管理端页面由 AI 生成，交互细节和作者预期不一致] → 每张页面都按任务里的验证方式走一遍，改动以意见的形式提出。
